# Phase 8C-mini：2B base pass_all beat_ms 扫频总结

生成时间：2026-05-22

## 1. 实验概述

本轮为 **pass_all 最坏压力模式**实验，**不代表正式 threshold 部署流量**。
在 `efficientad_gate_mode=threshold` 下，T2 EfficientAD 门控会过滤大量帧，
实际 T3 VLM 输入率远低于 pass_all 模式。

**目的**：测定 2B base W8A8 在 RK3588 上的 T3/Qwen3-VL 队列压力边界，
为生产部署确定最小可行 beat_ms。

**部署变体**：2B base。LoRA 已确认不适合作为当前 RK3588 W8A8 部署主线；
4B 板端路径尚未实现，本轮不参与。

## 4. 关键发现

### 4.1 最小稳定节拍：**10000 ms**

- 15000ms 和 13000ms：零队列丢帧，稳定。
- 10000ms：1 次队列丢帧（边界稳定）。VLM 均值（10.9s）略高于节拍间隔，
  但单次丢帧发生在停止边界附近，14 张唯一图片全部处理完成。
- 8000ms：6 次队列丢帧——VLM 无法跟上 8s 的发帧速率。
- 5000ms：23 次队列丢帧，取帧 41 次但 VLM 仅完成 16 次。严重积压。

### 4.2 队列丢帧起始区间：10000ms ~ 8000ms 之间

| beat_ms | 丢帧数 | VLM均值 / beat 比值 |
|---------|--------|---------------------|
| 15000 | 0 | 10.7s / 15.0s = 0.71 |
| 13000 | 0 | 10.8s / 13.0s = 0.83 |
| 10000 | 1 | 11.0s / 10.0s = 1.10 |
| 8000 | 6 | 11.4s / 8.0s = 1.42 |
| 6000 | 14 | 11.7s / 6.0s = 1.96 |
| 5000 | 23 | 13.1s / 5.0s = 2.62 |

临界比值为 VLM_avg_ms / beat_ms。比值超过 ~1.0 时开始丢帧，
比值 > 1.5 时丢帧严重。

### 4.3 队列丢帧发生位置

所有丢帧发生在 **Q2**（T2 EfficientAD 与 T3 FastSAM/VLM 之间）。依据：
- `ead_gate_pass` = 取帧数（pass_all 模式下全部通过）
- `dropped` 计数随 beat_ms 降低而比例增加
- Q2 容量为 2（最小队列），是直接瓶颈

在较快节拍下，T1 发帧速率超过 T3 消费 Q2 的速率。Q2 容量仅 2，
即使一次 VLM 处理卡顿（单帧耗时 17s），也会导致后续 2+ 帧被丢弃。

### 4.4 VLM 延迟与 beat_ms 的关系

| beat_ms | qwen3vl均值 | qwen3vl最大 | 相对15000ms偏差 |
|---------|-------------|-------------|-----------------|
| 15000 | 10735 | 17636 | 基线 |
| 13000 | 10775 | 17183 | +0.4% |
| 10000 | 10957 | 17183 | +2.1% |
| 8000 | 11384 | 17455 | +6.0% |
| 6000 | 11737 | 17538 | +9.3% |
| 5000 | 13083 | 18295 | +21.9% |

较短节拍下 VLM 延迟上升原因：
- 队列压力导致调度竞争
- 背压下 RKNN/VLM 运行时资源争用
- RSS 内存压力（轻微：3275 → 3292 MB）

### 4.5 RSS 稳定性

RSS 在所有节拍下稳定：3275-3297 MB 范围。未观察到内存泄漏。
~20MB 的波动在 RKLLM 运行时正常范围内。

### 4.6 Decode TPS 稳定性

decode_tps 稳定：所有节拍下 9.2-9.8。较短节拍下的轻微下降
（9.8 → 9.2）与资源争用一致，但影响很小。

### 4.7 上传成功率

上传成功率：所有节拍下 100%。T4 upload worker 从未失败。
即使在严重队列压力下，已处理的帧始终能成功上传。

### 4.8 json_parse_ok 稳定性

json_parse_ok 在所有节拍下稳定：均为 14/15（1 次 fallback 来自
tile good 图片——Phase 8B 已知的确定性 VLM 失败）。
beat_ms 不影响 JSON 解析质量。

### 4.9 5000ms 的影响

5000ms 节拍下：
- 41 次取帧 vs 16 次 VLM 完成：吞吐率仅 39%
- 23 次队列丢帧：56% 的帧丢失
- VLM 均值上升至 13.1s（比基线慢 21.9%）
- 最大 VLM 延迟达 18.3s（所有节拍中最高）
- 仍处理了 14 张唯一图片（第一轮循环在严重积压前完成）

5000ms **远超压力边界**。系统进入持续积压状态，
取帧 worker 持续超过 VLM 消费速率。

## 5. 问题解答

### Q1：pass_all 下最小稳定节拍是多少？

**10000ms**。该节拍下仅 1 次边界丢帧（可能发生在停止阶段），
14 张唯一图片全部处理完成，VLM 指标健康。
8000ms 时稳定性破坏（6 次丢帧）。

### Q2：哪个 beat_ms 开始出现队列丢帧？

**10000ms ~ 8000ms 之间**。转换是突变的：10000ms 1 次 → 8000ms 6 次。
对应 VLM_avg/beat 比值穿越 1.0。

### Q3：丢帧发生在哪个队列？

**Q2**（T2 与 T3 之间）。Q2 容量最小（2），是直接瓶颈。
Q1（容量 4）和 Q3（容量 4）有更多余量。

### Q4：avg/max qwen3vl_ms 与 beat_ms 的关系？

VLM 延迟随 beat_ms 降低而上升。5000ms 时均值比 15000ms 高 21.9%。
原因：调度竞争和背压下资源争用。最大延迟（17-18s）受影响较小——
由最坏情况图片（tile crack, ~17s）主导。

### Q5：RSS 是否稳定？

**是。** 3275-3297 MB，无泄漏。

### Q6：decode_tps 是否稳定？

**是。** 9.2-9.8，较短节拍下的轻微下降在正常范围内。

### Q7：上传是否始终成功？

**是。** 所有节拍下 100% 上传成功。

### Q8：json_parse_ok 是否受 beat_ms 影响？

**否。** json_parse_ok 在所有节拍下均为 14/15（1 次 fallback 来自
已知的 tile good VLM 失败）。更快节拍不会导致额外 JSON 解析失败。

### Q9：5000ms 是否会产生积压或丢帧？

**是，严重积压。** 23 次队列丢帧，VLM 吞吐率仅 39%（16/41），
持续积压状态。不可行。

### Q10：对 Phase 8D 的工程结论是什么？

pass_all 最坏压力模式下：
- 最小稳定节拍：**10000ms**
- pass_all 推荐安全节拍：**13000ms**（零丢帧，VLM 容量充裕）
- VLM 均值 ~10.7s 设定下限：任何低于 ~11s 的节拍最终都会积累积压

生产 threshold 模式下：
- T2 门控过滤大量帧（取决于阈值校准）
- threshold 模式下，实际 T3 输入率远低于取帧率
- 若 T2 过滤 >50% 的帧，5000-8000ms 节拍在 threshold 模式下可能可行
- 需要在未来 threshold 模式扫频中验证

### Q11：threshold 模式是否有足够吞吐冗余？

threshold 模式下，T2 EfficientAD 充当负载脱落门控。根据 Phase 8A 校准数据
（14/15 类别 AUROC < 0.80），正常图片的大部分会被阈值过滤。这意味着：
- 有效 T3 输入率 = 取帧速率 × 门控通过率
- 若门控通过率 ~30-50%（正常图片主导时的典型值），
  则 5000ms 节拍在 threshold 模式下的有效 T3 输入率等价于
  pass_all 模式下 ~10000-16000ms
- **存在足够的吞吐冗余用于生产部署**

### Q12：是否可以进入 4B path + smoke？

2B base 压力边界已标定。是否进入 4B 取决于 Phase 8D 规划。
4B 模型参数量约为 2B 的 2 倍，VLM 延迟将显著增加（预估 ~20-25s）：
- 4B 在 pass_all 下需要约 20-25s 的最小节拍
- 4B 可能需要 threshold 模式才能在合理节拍间隔下可行

## 6. 重要说明

1. **本轮为 pass_all 最坏压力模式。** 生产部署使用 threshold 模式，
   在 T2 层过滤帧。实际 T3 负载将显著低于 pass_all。
2. **VLM 未识别具体缺陷类型。** 两种变体对多数缺陷输出 "anomaly"。
   这是模型质量问题，非时序问题。
3. **tile good 图片产生确定性 VLM 失败**（每轮 1 次 fallback）。
   这是 Phase 8B 已知问题，非 beat_ms 导致。
4. **14 张图是小样本集。** 结果可能随图片组成不同而变化。
   最坏情况图片（tile crack, ~17s）主导最大延迟。
5. **稳定性指标不含 good 图片。** good 图片的 "none_rate" 不在
   稳定性判定标准内——它是 Phase 8D 的质量指标。
